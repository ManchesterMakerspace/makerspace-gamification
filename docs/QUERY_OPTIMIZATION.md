# Interactive Mongo reads

The optimized read path reduces Mongo round trips and returned records for conversations, skill displays, quest discovery and operator metrics. It uses fixed aggregation pipelines, projections, compound indexes and TTL in existing collections. It adds no source writes or indexes, external search service, direct change stream or database-wide privilege. Source and owned databases may remain on separate clusters.

## Query behavior

- Source identity joins return one validated member/mapping and reject duplicate live mappings in either direction. Request-local batching shares identity reads across candidates and history authors; identity and permission facts are never cached across requests.
- `query_makerspace` applies literal search, caller-only clearance and enabled-parent joins before sorting and taking `limit + 1`. Its existing 1–25 result limit, truncation signal, two-second read deadline and three-call/thirty-second conversation budget remain. A catalog exceeding 1,000 records no longer makes a valid narrow query unavailable.
- Public community-count answers use fixed `checkins` and `members` aggregations with a two-second deadline. Check-ins count distinct nonempty `uid` field values from `timeOf` across seconds, milliseconds and BSON date values; member counts use `startDate` and exclude merged duplicates. Only the final count and approved timeframe leave the source query. Space-use totals enter the low-latency interactive lane, where Qwen varies plain member wording; Python validates the count/timeframe and falls back deterministically. The original question, source identifiers, and ambient history never enter inference. This path remains available to any human user in a DM or joined channel without identity lookup or Ledger participation. It adds no source writes, indexes or Mongo grants. Because `checkins` has no declared time index, large scans can time out and return no answer.
- Highest cleared skill reads the caller's current cleared tools and prerequisite ancestors using `$lookup`/`$graphLookup`. Rails may store prerequisites as strings or BSON ObjectIds; unresolved string IDs expand in normalized, visited batches under one two-second budget. Native-ID closures usually need one source aggregation; string/mixed closures can need additional frontier batches. Python computes longest DAG depth and excludes cycles, missing dependencies and disabled parents; traversal distance does not establish skill depth or mastery.
- Quest discovery reads indexed publication heads and acceptance pointers in normalized-title/revision/ID pages, joins current revisions and filters eligibility before retaining display results. Publication heads use `revision` and acceptances use `quest_revision` as the tie key before document ID. The whole discovery call has a two-second deadline. Display heads never authorize acceptance, review or completion. Prepare legacy metadata before enabling this path; `LEDGER_OPTIMIZED_READS=false` provides the unprepared-data compatibility path.
- Conversation history reads newest-first pages using numeric Slack timestamp order plus ID, batches current authors and continues until six authorized entries or exhaustion. Current request, consent-generation mismatch, restricted rank facts, expired bodies and unrelated ambient records remain excluded; edits/deletions take effect at delivery.
- Operator metrics aggregate counts/statuses on the server. The existing latency-array response remains a narrow projected read; no historical message, prompt or evidence bodies are returned for counts.

## Display cache

`ledger_catalog` stores immutable generations with per-shop/per-tool `display_fields`, prerequisite labels and an atomic `catalog-display-active` manifest. Only names, descriptions, wiki links, shop bindings and prerequisite topology enter this read model. It stores no identity, consent, membership, staff scope, clearance or safety-status snapshot.

Refreshes use allowlisted source projections in 200-record keyset pages and write generation records in batches of 200, with a sixty-second overall deadline checked between pages/batches. Freshness starts at the first source read and lasts at most 300 seconds. The existing accounting startup, thirteen-minute reconciliation and shop/tool MQTT changes coalesce a durable `catalog_refresh` inbox job. Broker outage does not prevent live reads or periodic recovery. Refresh events received while the job is working coalesce into that job; the periodic sweep and freshness fallback cover display changes it misses.

A complete refresh publishes the manifest transactionally; interrupted writes retain the previous manifest. Older refreshes and workers that lost their job lease cannot overwrite a newer publication. Unchanged source display content reuses the generation; near expiry or missing records rebuild it. Generation records expire after 24 hours through Mongo TTL, including incomplete/retired generations, without an application delete grant. Readers verify the selected generation's expected record counts and expiry headroom, then retrieve only labels/topology in source-ID order. Stale, missing, malformed, incomplete or failed cache reads use the live display path.

Skill rendering rechecks displayed tools and their parents, current prerequisites, availability and caller clearances from sources. Deleted/disabled/moved tools are omitted; a moved tool appears in its new shop after refresh. Cached labels may lag within the freshness window, but “Next step” uses current prerequisite IDs. Failed safety reads never fall back to cached permission facts. Highest-current-skill and progression calculations stay live.

## Preparation and rollout

Python defaults `LEDGER_OPTIMIZED_READS` to `true`; Compose and `.env.example` default it to `false` for staged deployments. Both read flags reach every bot service. Keep all application processes on the legacy setting until preparation and verification finish.

1. Review the exact [Mongo grants](MONGODB_ACCESS.md). The only additional action/resource is `CREATE_INDEX` on `ledger_catalog`; source users remain `find` only. Provision it deliberately through an authorized operator.
2. Run `ledger prepare-reads --verify` using the configured source/owned credentials. It creates additive owned indexes, backfills quest-head/acceptance display fields, challenge/open-quest title keys and numeric context ordering, then refreshes display metadata. Preparation counts include updated heads, acceptances, display titles and context records plus catalog availability/shop/tool counts. It neither calls Slack/inference nor changes source records, consent, XP or accounting history.
3. Inspect preparation counts, verification mismatches and `expected_differences`. Shadow comparisons cover source queries, highest skill, skill text, quest options and metrics for up to 25 opted-in members. The two fixed legacy catalog-size rejections followed by optimized success are reported as expected differences. Genuine errors, authorization/result differences and unavailable reads are mismatches, including when both paths are unavailable. Output contains safe case labels/counts, not source bodies or exception text. A nonzero mismatch count fails the command; concurrent source changes require investigation or a repeat in a quiet window.
4. Enable `LEDGER_QUERY_METRICS=true` for a measured pilot if desired. Compare command count, returned documents, reply bytes and latency on representative warm/cold requests, including members with extensive history and catalogs beyond 1,000 records. Local tests establish behavior, not production performance gains.
5. Set `LEDGER_OPTIMIZED_READS=true`, recreate the application processes and verify skills, quest search, consent/role loss and edited/deleted chat behavior. Publish the current bundled policy to any Google Doc override deliberately, then explicitly reload it; reserved deliveries keep their existing policy/text.

Preparation is idempotent. `LEDGER_OPTIMIZED_READS=false` restores the legacy read path; retain the additive indexes, metadata and TTL cleanup. No rollback deletes source records or rebuilds XP. Cached metadata becoming stale is an ordinary live-fallback condition, not authorization to serve stale safety information.

## Diagnostics and deployment verification

`LEDGER_QUERY_METRICS` defaults to `false`. Its PyMongo listener retains command/collection labels, command counts, returned cursor-document counts, BSON reply bytes, elapsed microseconds and failure counts. It stores/logs no filters, IDs, URIs, source bodies, prompts or credentials. Reply bytes include protocol/envelope overhead, rather than measuring just application payloads. Worker queue loops report process-wide interval totals every sixty seconds; preparation verification reports counter snapshots when instrumentation is enabled.

Use a disposable replica set for the opt-in integration tests and verify real Atlas credentials, server pipelines, index plans and representative data before rollout. This repository's local validation does not perform live Atlas, Google Doc, Slack or Qwen checks. Unindexed source filters can still examine many source records even when few documents are returned; this change intentionally does not provision source indexes. Search indexes, dedicated tiers, new direct streams and broad worker polling changes are outside this rollout.

`$graphLookup` cannot project its foreign documents during traversal, so it temporarily holds complete tool ancestors on the server. The next stage immediately reduces them to allowed skill fields before deduplication and client output. Verify memory and deadline behavior for wide/deep prerequisite graphs on Free/Flex; their lack of disk spilling makes this a deployment gate. The optional Mongo fixtures compare real pipeline results and representative `executionStats` output counts, without asserting fewer examined source documents.
